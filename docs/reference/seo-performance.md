# Webiston — SEO & Performance

> Webiston's traffic is organic search on Uzbek-language programming queries.
> SEO and Core Web Vitals are product features here, not an afterthought — and
> because this is also the owner's portfolio, a slow or badly-rendered page is a
> credibility cost as well as a ranking cost.

---

## 1. What already exists (do not rebuild)

| Concern           | Where                                                        |
| ----------------- | ------------------------------------------------------------ |
| Base metadata     | `src/app/layout.tsx` — `metadataBase`, title template, description, OpenGraph, Twitter, JSON-LD |
| Sitemap + robots  | `next-sitemap.config.js`, generated in `postbuild`; `generateRobotsTxt: true` |
| Tool URL list     | `tools-list.json`, regenerated by `scripts/update-tools-list.js` |
| Search index      | `scripts/build-search-index.js` (postbuild)                   |
| PWA manifest      | `src/app/manifest.ts`                                         |
| Redirects         | `next.config.ts` — `/docs/:path*` → `/books/:path*` (permanent) |

The `postbuild` chain is load-bearing: **tools list → sitemap → search index**.
A new tool that is not in `tools-list.json` is not in the sitemap.

## 2. The rendering rule

**101 of 208 `.tsx` files in `src/` are `'use client'` (49%).** On a site whose
value is server-rendered prose and static tool UIs, that is the primary
performance debt.

- `'use client'` belongs on the **smallest interactive leaf**, never on a
  `page.tsx` or `layout.tsx`.
- Before adding it, ask: does this component use state, effects, event handlers,
  or a browser API? If it only renders props, it stays on the server.
- A client boundary is **contagious downward** — everything imported below it
  becomes client too. Placing it high is how 49% happens.
- Books (`content/**`) are read-mostly. The chapter body should be server-
  rendered; only the TOC, search, and image zoom need hydration.
- Tools are inherently interactive — but the tool *page shell* (title,
  description, info section, SEO copy) does not have to be.

## 3. Metadata rules

- **Every route exports `metadata`** (or `generateMetadata` when it depends on
  params). A tool page or a chapter with no title/description inherits the
  generic site title and competes with itself in search results.
- Titles are written for the query, not for the app: *"JSON Formatter — onlayn
  JSON formatlash"* beats *"JSON Formatter | Webiston"*.
- Descriptions in Uzbek for `uz` routes, English for `en` routes.
- `alternates.languages` should declare the uz/en pair so Google links them
  instead of treating them as duplicates. Not wired today — backlog item.
- `<html lang>` is hardcoded `"uz"` (`src/app/layout.tsx:394`) — wrong on every
  English page. See `content-i18n.md § 1`.

## 4. Images

`next.config.ts` sets `images: { unoptimized: true }` — Next's image optimizer
is **off**. That means every image ships at its authored size and format.

Consequences to respect:

- Compress and size assets **before** committing them to `public/`.
- Always set explicit `width`/`height` (or `fill` + a sized container) — without
  the optimizer there is nothing else preventing layout shift (CLS).
- Prefer modern formats (WebP/AVIF) at author time since the pipeline will not
  convert for you.
- If a hero or book cover is the LCP element, it needs `priority`.

Turning the optimizer back on is a real option, but it has deployment
implications (`output: "standalone"`) — that is an ADR-sized decision, not a
drive-by change.

## 5. Bundle discipline

Heavy dependencies already in the tree: `pdfjs-dist`, `mammoth`, `docx`,
`katex`, `shiki`, `leaflet` + `react-leaflet`, `framer-motion`, `flexsearch`.

- **Every one of these must be dynamically imported** at the tool or component
  that needs it. A PDF parser has no business in the homepage bundle.
- `next/dynamic` with `ssr: false` for anything touching `window`.
- When adding a dependency, state in the PR/commit which route pays for it.
- Before claiming a bundle improvement, measure: build, then compare the route
  sizes Next prints. A plausible-sounding chunking change that measures zero is
  a change you should revert.

---

## 6. Structured data

`layout.tsx` already emits JSON-LD. Extend it where it earns rich results:

- Book chapters → `Article` / `TechArticle` with `inLanguage: "uz"`.
- Tool pages → `SoftwareApplication` or `WebApplication`.
- The books index → `ItemList`.

Validate with Google's Rich Results Test before shipping. Invalid JSON-LD is
worse than none.

---

## 7. Verification

Do not report an SEO or performance improvement without one of these:

1. `pnpm build` output — route sizes and First Load JS, before vs after.
2. A Lighthouse run on the specific route (mobile profile), before vs after.
3. For metadata: view-source or the deployed URL in a rich-results validator.

"Should be faster" is not a result.
